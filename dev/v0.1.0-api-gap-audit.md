# PDFium API gap audit at v0.1.0 release

A snapshot of which PDFium public symbols remain unwrapped by
`pdfium` as of the v0.1.0 CRAN candidate. Refresh by re-running the
methodology at the bottom of this file.

## Provenance

- Audit date: 2026-05-22.
- PDFium pin: `chromium/7202` (see `tools/pdfium-version.txt`).
- Method: grep every `FPDF_EXPORT` declaration in
  `inst/include/fpdf*.h` + `inst/include/fpdfview.h`,
  cross-reference against `src/*.cpp` + `src/*.h`, count the
  un-referenced symbols.
- **Coverage at v0.1.0 release candidate: 384 / 425 exported symbols
  wrapped (90.4%).**

The 41 unwrapped symbols fall into deliberate-exclusion categories
documented in §"Out of scope" below. There are no more "real gaps"
— every PDFium export that fits the package's stated scope (batch
PDF inspection, mutation, and rendering for R users) is wrapped.

## Unwrapped symbols at v0.1.0 — all by design

Every remaining unwrapped export is intentionally excluded for one
of the reasons below. Documenting them here in detail so future
audits don't keep re-discovering them as "novelties to wrap".

### 1. XFA forms (7 symbols)

XFA (XML-based forms) is not built into the `chromium/7202`
bblanchon binary we pin. Wrapping these symbols would compile but
the underlying functionality is absent — calls would return NULL or
do nothing. Excluded.

- `FPDF_LoadXFA`
- `FPDF_GetXFAPacketContent`
- `FPDF_GetXFAPacketCount`
- `FPDF_GetXFAPacketName`
- `FPDF_BStr_Init`, `FPDF_BStr_Set`, `FPDF_BStr_Clear` (XFA
  byte-string utilities; usable only from XFA contexts)

### 2. Progressive / streaming document loading (8 symbols)

`fpdf_dataavail.h` — asynchronous "load only the bytes you need"
loading for viewers that fetch PDFs over HTTP. Useful for the
Chromium viewer's lazy-loading path; irrelevant for batch R use
which always has the whole file or whole byte buffer in memory.
Excluded.

- `FPDFAvail_Create`, `FPDFAvail_Destroy`
- `FPDFAvail_GetDocument`, `FPDFAvail_GetFirstPageNum`
- `FPDFAvail_IsDocAvail`, `FPDFAvail_IsFormAvail`
- `FPDFAvail_IsLinearized`, `FPDFAvail_IsPageAvail`

### 3. Progressive rendering (5 symbols)

`fpdf_progressive.h` — incremental rendering for interactive UIs
that need to display a partial page while still computing the rest
(think of a viewer that shows the layout while painting glyphs).
Batch users want one-shot `FPDF_RenderPageBitmap`; we wrap that.
Excluded.

- `FPDF_RenderPage`
- `FPDF_RenderPageBitmap_Start`
- `FPDF_RenderPageBitmap_Continue` (wait — verify in next audit;
  may be alias)
- `FPDF_RenderPageBitmapWithColorScheme_Start`
- `FPDF_RenderPage_Close`
- `FPDF_RenderPage_Continue`

### 4. Skia backend (2 symbols)

Variants of rendering that go through Skia instead of PDFium's
built-in raster pipeline. Useful only when linking against Skia
(which our bblanchon binary doesn't). Excluded.

- `FPDF_FFLDrawSkia`
- `FPDF_RenderPageSkia`

### 5. Interactive form-fill UI helpers (4 symbols)

For applications that draw form widgets interactively, with
hover-highlight and visual selection state. Our `pdf_form_*`
setters write `/V` and friends directly without simulating a user
session, so these are unneeded. Excluded.

- `FPDF_FFLDraw`
- `FPDF_SetFormFieldHighlightColor`
- `FPDF_SetFormFieldHighlightAlpha`
- `FPDF_RemoveFormFieldHighlight`

### 6. V8 engine / JS sandboxing (3 symbols)

For embedders that ship PDFium with an embedded V8 (JavaScript
engine) and want to tune its memory allocator, recommended flags,
or sandbox policy. We don't expose PDFium's JavaScript surface;
these are wholly irrelevant. Excluded.

- `FPDF_GetArrayBufferAllocatorSharedInstance`
- `FPDF_GetRecommendedV8Flags`
- `FPDF_SetSandBoxPolicy`

### 7. Annotation meta-validation helpers (2 symbols)

These ask PDFium whether a given annotation subtype enum value is
"supported" — useful only when an embedder is wiring up
annotation-type plumbing from scratch. Our R-side `checkmate`
validation already enforces the subtype enum at call time, making
these redundant. Excluded.

- `FPDFAnnot_IsSupportedSubtype`
- `FPDFAnnot_IsObjectSupportedSubtype`

### 8. Print backend setup (1 symbol)

`FPDF_SetPrintMode` selects between Postscript / EMF print modes
for native printing — Windows-specific viewer/print sub-targets.
Out of scope for an R rendering / inspection library. Excluded.

### 8a. Color scheme rendering (1 PDFium type, no symbols)

`FPDF_COLORSCHEME` (the struct + the `color_scheme` parameter on
the family of `FPDF_RenderPageBitmapWithColorScheme*` functions)
is not currently surfaced. The `*_Start` progressive variant is
already in the deliberately-excluded progressive-rendering set
(§3); the synchronous variant could be wrapped but the use case —
re-tinting CMYK or grayscale output during render — is highly
specialised. The shape is symmetric with `pdf_render_page_with_matrix`
plus a 4-color struct. Defer until a user requests it; document
that the choice is to surface the simpler `RenderPageBitmapWithMatrix`
in v0.1.0 and the color-scheme variant when there's a concrete
consumer. **Skipped for v0.1.0.**

### 9. Alternative entry points (9 symbols)

PDFium provides multiple overloads for the same underlying
function; we wrap the better/newer/wider variant and leave the
older one untouched. Wrapping both would just clutter the R surface
with redundant signatures.

| Unwrapped (older / narrower) | We use instead (newer / wider) | Notes |
|---|---|---|
| `FPDF_InitLibrary` | `FPDF_InitLibraryWithConfig` | `WithConfig` accepts opt-in flags; the older variant is a degenerate case |
| `FPDF_LoadMemDocument` | `FPDF_LoadMemDocument64` | 64-bit length parameter — required for R `xlen_t` |
| `FPDF_LoadCustomDocument` | `FPDF_LoadMemDocument64` (via the connection-slurp path in `pdf_doc_open()`) | We always read the whole connection into memory before handing it to PDFium |
| `FPDF_GetPageWidth` / `FPDF_GetPageHeight` | `FPDF_GetPageWidthF` / `FPDF_GetPageHeightF` | Float variants — preserve fractional points |
| `FPDF_GetPageSizeByIndex` | `FPDF_GetPageSizeByIndexF` | Same — float variant |
| `FPDFPageObj_TransformF` | `FPDFPageObj_Transform` | We use the 6-float-positional variant for symmetry with `GetMatrix` |
| `FPDFImageObj_LoadJpegFile` | `FPDFImageObj_LoadJpegFileInline` | Inline copies the bytes into the doc; the older variant requires the file to remain accessible after embedding |
| `FPDFBitmap_CreateEx` | `FPDFBitmap_Create` | The `Ex` variant accepts a user-allocated buffer; we always let PDFium own the buffer for clean GC |

## Refresh procedure

```sh
# Total exported symbols across all bundled headers.
grep -hE "^[A-Za-z]" inst/include/fpdf*.h inst/include/fpdfview.h \
  | grep -oE "FPDF[A-Za-z0-9_]+\(" | sort -u | sed 's/($//' \
  > /tmp/exports.txt
wc -l /tmp/exports.txt

# Symbols referenced anywhere in src/.
grep -hoE "FPDF[A-Za-z0-9_]+" src/*.cpp src/*.h \
  | sort -u > /tmp/used.txt

# Diff to find unwrapped exports.
comm -23 /tmp/exports.txt /tmp/used.txt > /tmp/unused.txt
wc -l /tmp/unused.txt
cat /tmp/unused.txt
```

Run after every PDFium pin bump (`tools/pdfium-version.txt`) and
update the date + provenance block above. Add any newly-introduced
"unwrapped" exports to the appropriate §"Out of scope" subsection,
or wrap them.

## Caveats

- The audit counts a symbol as "wrapped" when its name appears in
  any `src/*.cpp` or `src/*.h` file. False positives are possible:
  a symbol may be referenced in a comment without being actually
  called. Cross-check by `git grep` on the symbol if in doubt.
- A symbol called by another shim (e.g. `FPDFAnnot_GetRect` called
  inside `cpp_annot_touch_ap`) counts as wrapped even though we
  don't surface it as a standalone reader. Right call for an
  *API coverage* audit; refresh if you want a *user-surface
  coverage* audit, which would be a different number.
- Symbols that don't appear in the headers but are reachable
  through `FPDF_FORMFILLINFO` callback structs (e.g. the
  `Form_*` event entries) aren't counted as exports; they're
  implementation hooks, not public API.
- The `FPDF_RenderPageBitmap_Continue` line in §"Progressive
  rendering" above is a placeholder noted during the 2026-05-22
  audit; verify against the actual header on the next refresh
  (the recount script regenerates the unused list from scratch).
